02 / The problem

Search needs both meaning and precision.

Pure keyword retrieval is strong when a query contains the exact terms stored in a document, but it can miss conceptually related language. Dense vector retrieval handles semantic similarity, but can be weaker for exact identifiers, URLs, domains, and precise lexical constraints.

NexusSearch explores a combined approach: Elasticsearch BM25 and Qdrant dense-vector retrieval execute concurrently, after which their ranked results are merged with Reciprocal Rank Fusion and passed through additional ranking signals.

03 / System architecture

Separate the fast path from the heavy path.

The architecture keeps user-facing search separate from crawling, model inference, and enrichment work. Nginx acts as the API gateway, FastAPI services expose domain-specific APIs, and RabbitMQ decouples URL ingestion from background processing.

The system is containerized through Docker Compose and uses separate storage systems for relational state, lexical indexing, vector search, and caching.

04 / Retrieval engineering

Two search engines. One ranked result set.

The retrieval layer does not directly add BM25 scores to vector similarities because those scores live in different numerical spaces. Instead, the system retrieves candidates independently and combines their rank positions using Reciprocal Rank Fusion (RRF).

Lexical retrieval

Elasticsearch 8.13.4 runs BM25 queries over indexed title, description and content fields, with a custom analyzer and additional trust/popularity/freshness signals.

Dense retrieval

Qdrant stores normalized 1024-dimensional BGE-M3 embeddings using cosine distance. The implementation uses asymmetric passage: and query: prefixes.

Reciprocal Rank Fusion
RRF(d) = Σ 1 / (60 + rankm(d))
Rank positions from BM25 and vector retrieval are fused before additional multi-factor ranking.
05 / Ingestion pipeline

Heavy work happens off the request path.

A submitted URL enters RabbitMQ and is processed by dedicated background workers. The crawler extracts content, then the AI pipeline performs summarization, trust scoring and embedding generation before the resource becomes active.

The important state transition is deliberate: PostgreSQL keeps the resource unverified until the required vector and full-text indexing work succeeds. This prevents half-indexed resources from presenting themselves as searchable.

06 / Engineering challenges
01 · Memory ceilings

Multiple BGE-M3 model instances alongside Elasticsearch, PostgreSQL and the rest of the stack created constrained-environment memory pressure. The implementation uses CPU-only PyTorch, lazy loading, thread-safe initialization and a shared model cache.

02 · Cross-store consistency

Interrupted ingestion could leave PostgreSQL, Elasticsearch and Qdrant at different stages. Transaction boundaries were adjusted so activation follows successful indexing rather than preceding it.

03 · Incompatible score spaces

BM25 scores are unbounded while cosine similarities are bounded. Direct addition would let one retrieval engine dominate, so rank-based RRF is used for the first-stage merge.

04 · Stale test artifacts

Interrupted distributed tests could leave orphaned search records behind. Deterministic cleanup across PostgreSQL, Elasticsearch and Qdrant was added before strict baseline assertions.

08 / Current limitations
Knowledge graph endpointThe /explore frontend is currently disconnected because the graph router is not registered in the search application.
Single-node ElasticsearchThe development Compose configuration uses a single Elasticsearch node; the configured replica contributes to a yellow development health state.
Cold-start model latencyLoading BGE-M3 into CPU memory on a cold container can take tens of seconds before normal query latency resumes.
Monitoring gapPrometheus configuration lacks dedicated Redis and PostgreSQL exporter containers.

What this project taught me about building AI systems.

NexusSearch moved beyond implementing an individual model or API. The difficult part was designing the boundaries between retrieval engines, databases, asynchronous workers, model inference, failure recovery and the interface a user actually interacts with.

The result is a project where the interesting engineering is in the system around the AI: how data enters, how it is represented twice for two retrieval strategies, how results are reconciled, and how the system behaves when individual components fail.
